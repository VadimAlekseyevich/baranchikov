# Замеры масштабирования — GitHub Actions, 21.10.2026

Источник: [успешный запуск GitHub Actions](https://github.com/VadimAlekseyevich/baranchikov/actions/runs/39634448905), job `docker-integration`, артефакт `lab5-benchmark`.

Условия: Ubuntu GitHub-hosted runner, Docker Compose, Java 25, **один замер** на конфигурацию, 120 запросов `GET_OPEN_ORDERS` на точку, 6 конкурентных потоков, 40 прогревочных запросов. Для каждого слоя масштабируется только он (1, 2, 3 реплики), другие слои — по одной реплике. Внешний протокол UDP текстовый, внутренний Protobuf+TCP. Фиксированной производительности оборудования GitHub runner не гарантирует.

Показатель `rps`: успешных запросов/сек. `p50_ms` и `p95_ms`: задержка запроса в миллисекундах. Ошибки на всех точках = **0**.

Полные данные: [benchmark-results.csv](benchmark-results.csv). Вывод сравнения: [benchmark-comparison.md](benchmark-comparison.md).

**Наблюдения:**

- `facade`: 205,78 → 206,16 → 265,25 RPS (3 реплики дают около 1,29× от 1 реплики).
- `business`: 268,70 → 378,75 → 281,76 RPS (2 реплики около 1,41×, 3 реплики лишь около 1,05× от 1).
- `storage`: 300,01 → 334,05 → 344,11 RPS (3 реплики около 1,15×).

Итог: слоистая архитектура позволяет независимо масштабировать компоненты, но **линейного ускорения нет**. Все обращения к данным проходят через единственный сервер H2, поэтому он является общей точкой ограничения. Величины зависят от нагрузки, очередей, DNS, CPU и состояния виртуальной среды. Отдельная точка — только один пробег; для статистической точности повтори скрипт несколько раз на собственном ПК с одинаковым окружением.

Ручное повторение: в `lab5` выполнить `benchmark.cmd` (Windows) или `sh benchmark.sh` (Linux/macOS); свежие значения появятся в `benchmark-results.csv` и `benchmark-comparison.md` в корне `lab5`.
