# Лабораторная работа №5 — слоистая архитектура

Лабораторная продолжает `lab4`.

По заданию систему нужно разделить на слои, выделить интерфейсы взаимодействия между ними и отдельно покрыть каждый слой тестами.

## Архитектура

```text
UDP transport
UdpExchangeServer / UdpExchangeClient
        |
        | Exchange
        v
business / application
ExchangeService
        |
        | ExchangeRepository
        v
persistence
H2ExchangeRepository
        |
        v
       H2
```

### Транспортный слой

Пакет `org.example.exchange.udp`.

Он отвечает только за UDP: принимает и отправляет датаграммы, разбирает протокол и вызывает интерфейс `Exchange`.

`UdpExchangeServer` больше не создаёт H2-хранилище самостоятельно и не зависит от конкретной реализации базы данных.

### Слой бизнес-логики

Класс `ExchangeService`.

Он отвечает за правила биржи:

- подключение и отключение клиентов;
- выставление и сопоставление ордеров;
- создание сделок;
- онлайн- и отложенные уведомления;
- координацию транзакции.

Слой зависит от интерфейса `ExchangeRepository`, а не от H2.

### Слой хранения

Интерфейс `ExchangeRepository` и реализация `H2ExchangeRepository`.

Этот слой отвечает за SQL и сохранение ордеров, сделок и отложенных уведомлений. Бизнес-правил сопоставления ордеров в нём нет.

### Сборка слоёв

`Main` является точкой композиции:

```text
H2ExchangeRepository -> ExchangeService -> UdpExchangeServer
```

Модели `Order`, `Trade`, `CurrencyPair` и другие являются общими объектами предметной области.

`PersistentExchange` оставлен как тонкий совместимый фасад, чтобы тесты предыдущих лабораторных продолжали работать. Внутри он только собирает `ExchangeService` и `H2ExchangeRepository`.

## Тестирование слоёв

Каждый слой проверяется отдельно:

- `UdpTransportLayerTest` — настоящий UDP-сервер и клиент, но вместо бизнес-логики используется тестовая реализация `Exchange`;
- `ExchangeServiceLayerTest` — бизнес-логика без UDP и без H2, с тестовым in-memory `ExchangeRepository`;
- `H2ExchangeRepositoryTest` — H2-хранилище напрямую, без UDP и без бизнес-слоя.

Кроме этого сохранены тесты предыдущих лабораторных: интеграционные UDP-тесты, restart/crash-тесты, многопоточный тест и Docker-тесты.

## Запуск из IDE / Maven

```bat
cd lab5
mvn test
```

## Запуск в Docker

Docker-часть из четвёртой лабораторной сохранена:

```bat
docker compose build
docker compose up -d exchange-server
docker compose ps
docker compose run --rm tests
```

Проверка сохранения H2 после перезапуска:

```bat
verify-persistence.cmd
```

Остановка:

```bat
docker compose down
```

Удаление вместе с тестовым volume:

```bat
docker compose down -v
```

## Что изменилось относительно lab4

В `lab4` класс `PersistentExchange` одновременно содержал бизнес-логику и JDBC-код, а UDP-сервер сам создавал конкретную реализацию биржи.

В `lab5` эти обязанности разделены:

```text
transport -> Exchange -> service -> ExchangeRepository -> H2
```

Поэтому каждый слой можно тестировать и заменять независимо от остальных.

## Контрольные вопросы

**Как правильно выделить слои?** По разным обязанностям системы. Сетевой код не должен заниматься SQL, бизнес-логика не должна знать детали UDP или конкретной БД, а слой хранения не должен решать бизнес-задачи.

**Пример слоистой архитектуры.** Транспортный слой принимает запрос, сервисный слой выполняет бизнес-правила, слой хранения читает и записывает данные.

**Преимущества и недостатки.** Плюсы — проще тестировать, менять реализации и понимать ответственность кода. Минусы — появляется больше интерфейсов, классов и промежуточного кода; для очень маленькой программы такая структура может быть избыточной.
