# Лабораторная работа №2 — встроенное хранилище данных

Вариант 1: биржа валют.

Работа продолжает функциональность lab1, но находится в отдельной папке lab2. Публичный Java-интерфейс биржи сохранён, а состояние перенесено из оперативной памяти во встроенную файловую БД H2.

## Реализовано

- лимитные BUY/SELL-ордера по валютным парам;
- частичное и полное исполнение;
- price-time priority;
- цена сделки равна цене уже находящегося в книге ордера;
- уведомления обоим участникам;
- хранение offline-уведомлений в БД и доставка после connect;
- сохранение открытых ордеров, сделок и недоставленных уведомлений между перезапусками;
- потокобезопасная работа клиентов из разных потоков;
- штатное закрытие через AutoCloseable;
- восстановление после аварийного завершения процесса.

## Хранилище

Используется embedded H2 через JDBC. Создаются три таблицы:

- exchange_orders — ордера и оставшееся количество;
- trades — совершённые сделки;
- pending_notifications — ещё не доставленные уведомления.

Подключение клиента и Java callback не сохраняются: это ресурсы текущего процесса. После перезапуска клиент снова вызывает connect, после чего получает накопленные уведомления.

## Транзакции

Каждый placeOrder выполняется одной JDBC-транзакцией:

1. новый ордер записывается в БД;
2. находятся встречные ордера;
3. обновляются остатки;
4. создаются сделки;
5. для обоих клиентов создаются pending_notifications;
6. выполняется commit;
7. после commit уведомления доставляются подключённым клиентам.

Уведомление удаляется из pending_notifications только после успешного вызова listener. Поэтому сделка и уведомление не теряются, если процесс завершится между фиксацией сделки и доставкой.

## Запуск

Открой папку lab2 как Maven-проект. Main.java можно запускать зелёной кнопкой IntelliJ IDEA.

Для тестов из lab2:

    mvn test

По умолчанию демонстрационный Main использует базу data/exchange.mv.db. Папка data и файлы H2 добавлены в .gitignore.

## Тесты

PersistentExchangeTest повторяет основные сценарии первой лабораторной: partial/full fill, цену сделки, уведомления, offline-клиента и приоритет цены.

PersistentExchangeConcurrencyTest повторяет проверку одновременной работы клиентов через ExecutorService и CountDownLatch.

PersistentExchangeRestartTest добавляет сценарии второй лабораторной:

- штатное завершение: биржа закрывается, создаётся заново с тем же файлом БД и состояние сравнивается;
- нештатное завершение: отдельный JVM-процесс записывает данные и завершается через Runtime.getRuntime().halt(0), то есть без close и shutdown hooks. Затем тест открывает ту же БД и проверяет сделку, остаток ордера и сохранённые уведомления.

## Ответы на контрольные вопросы

### 1. Как достигается сохранение состояния процесса после перезапуска?

Бизнес-состояние вынесено из оперативной памяти в файловую H2-БД. При новом запуске PersistentExchange подключается к тому же файлу и использует сохранённые ордера, сделки и уведомления.

### 2. Как достигается сохранность данных при нештатном завершении программы?

Изменения выполняются транзакциями и фиксируются через commit. Ордер, изменения остатков, сделка и записи уведомлений входят в одну транзакцию. Нештатный сценарий проверяется отдельным JVM-процессом, который завершается без штатного закрытия.

### 3. На что влияет сохранение состояния программы в хранилище?

Появляются дисковые операции, транзакции и дополнительная сложность работы с данными, поэтому увеличиваются задержки по сравнению с чистой оперативной памятью. Взамен система получает долговременность данных и восстановление после перезапуска.
