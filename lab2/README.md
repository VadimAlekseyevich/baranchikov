# Лабораторная работа №2 — встроенное хранилище данных

Вариант 1: **биржа валют**.

Эта работа является логическим продолжением первой лабораторной. В первой версии все состояние находилось только в оперативной памяти процесса. Во второй лабораторной тот же прикладной сценарий сохранён, но бизнес-состояние перенесено во встроенную файловую СУБД H2, чтобы оно переживало перезапуск программы.

Поэтому текущая папка `lab2` содержит и функциональность первой лабораторной, и новые требования второй. Отдельная папка `lab1` в репозитории больше не нужна: `lab2` является актуальной накопительной версией решения.

---

## 1. Суть лабораторной работы

Главная идея работы — показать разницу между состоянием процесса и долговременным состоянием системы.

В первой реализации ордера, сделки и недоставленные уведомления существовали только в Java-коллекциях. После завершения JVM они исчезали. Во второй реализации эти данные записываются в H2 через JDBC и фиксируются транзакциями.

После повторного запуска программа подключается к тому же файлу БД и получает то же бизнес-состояние, которое было успешно зафиксировано до завершения процесса.

При этом публичный Java-интерфейс биржи почти не меняется. Клиент по-прежнему работает с `Exchange`, а способ хранения скрыт внутри реализации `PersistentExchange`.

---

## 2. Что должна уметь система

Биржа поддерживает следующие сценарии:

- клиент может выставить лимитный ордер;
- ордер содержит валютную пару;
- ордер имеет направление `BUY` или `SELL`;
- ордер содержит количество валюты;
- ордер содержит лимитную цену;
- встречные заявки автоматически сопоставляются;
- поддерживается частичное исполнение;
- поддерживается полное исполнение;
- при сделке формируется объект `Trade`;
- оба клиента получают `TradeNotification`;
- если клиент offline, уведомление сохраняется;
- после следующего `connect` сохранённое уведомление доставляется;
- несколько клиентов могут обращаться к бирже из разных потоков;
- открытые ордера сохраняются между перезапусками;
- совершённые сделки сохраняются между перезапусками;
- недоставленные уведомления сохраняются между перезапусками;
- состояние восстанавливается после штатного завершения;
- состояние восстанавливается после нештатного завершения процесса.

## 5. Архитектура решения

Упрощённо система устроена так:

```text
Клиент
  |
  v
Exchange
  |
  v
PersistentExchange
  |
  +--> JDBC transaction
  |
  v
H2 file database
```

Отдельно существует callback-механизм уведомлений:

```text
PersistentExchange
  |
  +--> NotificationListener подключенного клиента
  |
  +--> pending_notifications, если клиент offline
```

Публичный API отделён от конкретного хранилища. Это важно для следующих лабораторных: поверх `Exchange` можно добавить сетевой слой, не меняя основной бизнес-сценарий клиента.

## 6. Пакет api

### 6.1. Exchange

`Exchange` — основной публичный интерфейс системы.

Он описывает операции, которыми пользуется клиент.

Основные методы:

### `connect(String clientId, NotificationListener listener)`

Считает клиента подключенным к текущему Java-процессу.

Сохраняет callback `NotificationListener` в памяти.

После подключения пытается доставить клиенту все сохранённые в БД уведомления.

Важно: сам listener в БД не сохраняется. Сериализовать Java callback между перезапусками бессмысленно, потому что он относится к конкретному процессу JVM.

### `disconnect(String clientId)`

Удаляет клиента из списка online-клиентов текущего процесса.

Данные клиента, его ордера и сделки при этом не удаляются.

### `placeOrder(...)`

Выставляет новый лимитный ордер и сразу пытается сопоставить его с существующими встречными ордерами.

Внутри этого метода выполняется основная бизнес-логика биржи и одна JDBC-транзакция.

### `getOpenOrders(CurrencyPair pair)`

Возвращает все ещё не исполненные полностью ордера по валютной паре.

Открытым считается ордер, у которого `remaining_quantity > 0`.

### `getTrades()`

Возвращает историю всех сделок.

---

### 6.2. NotificationListener

`NotificationListener` — функциональный интерфейс:

```java
void onTrade(TradeNotification notification);
```

Он играет роль callback-функции клиента.

Если клиент online, биржа вызывает listener после совершения сделки.

Если клиент offline, уведомление сохраняется в таблице `pending_notifications` и будет передано при следующем `connect`.

## 7. Пакет model

### 7.1. CurrencyPair

`CurrencyPair` описывает валютную пару, например:

```text
EUR/USD
USD/RUB
GBP/USD
```

Содержит:

- `base` — базовую валюту;
- `quote` — котируемую валюту.

Класс нормализует названия валют:

- удаляет лишние пробелы;
- переводит код в верхний регистр;
- запрещает пустые значения;
- запрещает одинаковые валюты в паре.

---

### 7.2. OrderSide

Перечисление направления заявки:

- `BUY` — покупка базовой валюты;
- `SELL` — продажа базовой валюты.

---

### 7.3. Order

`Order` — неизменяемое представление ордера, возвращаемое наружу.

Поля:

- `id` — идентификатор ордера;
- `clientId` — владелец;
- `pair` — валютная пара;
- `side` — BUY или SELL;
- `limitPrice` — лимитная цена;
- `originalQuantity` — первоначальный объём;
- `remainingQuantity` — неисполненный остаток.

Метод `isFilled()` возвращает `true`, если `remainingQuantity == 0`.

Пример:

клиент выставил BUY 10 EUR по цене 1.1000 USD.

После сделки на 4 EUR:

```text
originalQuantity  = 10
remainingQuantity = 6
```

---

### 7.4. Trade

`Trade` описывает уже совершённую сделку.

Поля:

- `id`;
- валютная пара;
- цена сделки;
- количество;
- id BUY-ордера;
- id SELL-ордера;
- id покупателя;
- id продавца.

Сделка является историческим фактом и после создания не изменяется.

---

### 7.5. TradeNotification

`TradeNotification` связывает сделку с конкретным получателем уведомления.

При одной сделке создаются два логических уведомления:

- покупателю;
- продавцу.

---

## 8. PersistentExchange

`PersistentExchange` — главная реализация второй лабораторной.

Она одновременно отвечает за:

- бизнес-логику matching;
- работу через JDBC;
- управление транзакциями;
- хранение состояния;
- восстановление после перезапуска;
- online/offline состояние текущего процесса;
- доставку накопленных уведомлений;
- синхронизацию потоков.

Класс реализует:

```java
Exchange, AutoCloseable
```

Благодаря `AutoCloseable` его можно использовать через `try-with-resources`.

## 9. Почему H2

Для лабораторной нужна встроенная СУБД.

H2 подходит, потому что:

- подключается как обычная Java-зависимость;
- не требует отдельного сервера;
- умеет хранить данные в файле;
- поддерживает SQL;
- поддерживает JDBC;
- поддерживает транзакции;
- состояние переживает завершение JVM.

Подключение формируется примерно как:

```text
jdbc:h2:file:<путь-к-базе>;DB_CLOSE_ON_EXIT=FALSE
```

`DB_CLOSE_ON_EXIT=FALSE` означает, что код не полагается на автоматическое закрытие БД shutdown hook-ом JVM. Это особенно важно для теста нештатного завершения.

Хранит ордера.

Основные поля:

| Поле | Назначение |

## 12. Алгоритм matching

Биржа использует принцип **price-time priority**.

Это означает:

1. сначала выбирается лучшая цена;
2. при одинаковой цене выигрывает более ранний ордер.

### Для входящего BUY

Ищется SELL:

```text
SELL.price <= BUY.limitPrice
```

Сначала выбирается минимальная цена SELL.

Если цены одинаковые, выбирается меньший `id`, то есть более ранний ордер.

### Для входящего SELL

Ищется BUY:

```text
BUY.price >= SELL.limitPrice
```

Сначала выбирается максимальная цена BUY.

При одинаковой цене также выбирается более ранний ордер.

---

## 13. Почему цена сделки равна цене resting-ордера

Resting order — это заявка, которая уже находилась в книге до прихода нового ордера.

В реализации фактическая цена сделки равна:

```text
resting.limitPrice
```

Пример:

```text
в книге: BUY 10 EUR по 1.1000
приходит: SELL 4 EUR по 1.0900
```

Заявки пересекаются, потому что продавец согласен продать по 1.0900 или выше, а покупатель уже предлагает 1.1000.

Сделка проходит по цене resting BUY:

```text
1.1000
```

---

## 14. Частичное исполнение

Количество сделки вычисляется как:

```text
min(incoming.remaining, resting.remaining)
```

Пример:

```text
BUY 10
SELL 4
```

Сделка:

```text
quantity = 4
```

После неё:

```text
BUY.remaining  = 6
SELL.remaining = 0
```

BUY остаётся открытым.

## 15. Что происходит внутри placeOrder

Это ключевой метод для защиты.

Последовательность следующая.

### Шаг 1. Валидация

Проверяются:

- clientId;
- валютная пара;
- направление;
- количество;
- цена.

Количество и цена должны быть положительными.

### Шаг 2. Захват блокировки

Берётся общий `ReentrantLock`.

Это не даёт двум потокам одновременно изменить одну и ту же книгу ордеров и одну транзакцию JDBC.

### Шаг 3. INSERT нового ордера

Ордер создаётся в `exchange_orders`.

База генерирует id.

### Шаг 4. Поиск лучшего встречного ордера

SQL выбирает один лучший matching-order с учётом:

- валютной пары;
- стороны;
- цены;
- остатка;
- price-time priority.

### Шаг 5. Расчёт количества сделки

Берётся минимальный остаток двух ордеров.

### Шаг 6. Обновление remaining_quantity

Остатки обоих ордеров обновляются в БД.

### Шаг 7. INSERT сделки

Создаётся запись в `trades`.

### Шаг 8. Создание уведомлений

Для покупателя и продавца создаются записи в `pending_notifications`.

Даже если оба клиента online, сначала уведомления фиксируются в БД.

### Шаг 9. Повтор matching

Если у входящего ордера остался объём, поиск следующего встречного ордера продолжается.

Один большой ордер поэтому может породить несколько сделок.

### Шаг 10. COMMIT

Все изменения фиксируются одной транзакцией.

### Шаг 11. Доставка online-клиентам

Только после успешного commit вызываются listeners подключенных клиентов.

## 16. Почему commit выполняется до callback

Это принципиальный момент.

Если сначала отправить уведомление клиенту, а потом записывать сделку, процесс может упасть между этими действиями:

```text
клиент получил сообщение
процесс упал
сделка не сохранилась
```

Получается противоречивое состояние.

В текущем решении сначала фиксируется факт сделки и pending-уведомления:

```text
transaction -> commit -> callback
```

Поэтому после crash информация о сделке не теряется.

---

## 17. Семантика доставки уведомлений

Используется семантика **at-least-once**.

Алгоритм:

1. уведомление записывается в БД;
2. транзакция фиксируется;
3. вызывается listener;
4. если listener завершился успешно, запись удаляется из `pending_notifications`;
5. удаление фиксируется отдельным commit.

Это означает:

- уведомление не должно потеряться;
- в редком crash-сценарии оно может быть доставлено повторно.

Например:

```text
listener получил сообщение
        |
        v
процесс упал до DELETE pending_notifications
```

После перезапуска уведомление всё ещё лежит в БД и придёт повторно.

Это нормальная и распространённая модель надёжной доставки.

Чтобы получить exactly-once, потребовалась бы более сложная схема с idempotency/deduplication на стороне клиента или отдельным протоколом подтверждений.

## 18. Online и offline состояние

Online-состояние хранится только в:

```java
Map<String, NotificationListener> onlineClients
```

Это сознательное решение.

Подключение — свойство текущего процесса, а не долговременное бизнес-состояние.

После перезапуска:

- старых Java listener уже не существует;
- клиент считается offline;
- ордера и сделки остаются;
- pending-уведомления остаются;
- после нового `connect` клиент получает накопившиеся уведомления.

---

## 19. Потокобезопасность

По методичке разные пользователи работают в разных потоках одного процесса.

Для защиты общего состояния используется один `ReentrantLock`.

Блокировка охватывает критические операции:

- изменение onlineClients;
- placeOrder;
- работу JDBC-транзакции;
- чтение состояния;
- доставку pending-уведомлений.

Почему не используются только `ConcurrentHashMap`?

Потому что операция выставления ордера состоит из нескольких связанных шагов:

```text
INSERT order
SELECT opponent
UPDATE order A
UPDATE order B
INSERT trade
INSERT notifications
COMMIT
```

Нужно защитить атомарность всей последовательности, а не отдельную операцию с Map.

---

## 20. Транзакционная целостность

`connection.setAutoCommit(false)`.

Следовательно, изменения не считаются завершёнными до явного:

```java
connection.commit();
```

Если во время SQL-операций возникает `SQLException`, выполняется:

```java
connection.rollback();
```

Поэтому не должно возникнуть состояния вида:

- ордер уменьшился, а сделка не записалась;
- сделка записалась только для одного участника;
- сделка существует, но pending-уведомление второго клиента не создано.

Ордер, его matching, сделки и pending-уведомления фиксируются согласованно.

## 21. Штатное завершение

`PersistentExchange` реализует `AutoCloseable`.

Пример:

```java
try (PersistentExchange exchange = new PersistentExchange(path)) {
    // работа
}
```

При выходе вызывается `close()`:

- выполняется commit;
- закрывается JDBC Connection.

После этого новый экземпляр `PersistentExchange` может открыть тот же файл и увидеть сохранённое состояние.

---

## 22. Нештатное завершение

Для проверки crash используется не просто вызов `close()`.

Тест запускает **отдельный JVM-процесс**.

В нём выполняются операции биржи, после чего вызывается:

```java
Runtime.getRuntime().halt(0);
```

`halt` принципиально отличается от обычного завершения:

- не выполняется обычная логика завершения приложения;
- не вызывается `close()` объекта биржи;
- не запускаются обычные shutdown hooks.

После этого основной тестовый процесс открывает ту же H2-БД и проверяет восстановленное состояние.

Так тест действительно проверяет, что ранее выполненные `commit` переживают аварийное завершение процесса.

## 23. Класс Main

`Main.java` нужен для демонстрационного запуска без тестов.

Он:

1. определяет путь к файлу БД;
2. создаёт `PersistentExchange`;
3. выводит количество восстановленных сделок и ордеров;
4. подключает покупателя и продавца;
5. выставляет два встречных ордера;
6. получает уведомления;
7. выводит новое состояние;
8. штатно закрывает биржу через try-with-resources.

По умолчанию используется:

```text
data/exchange
```

H2 создаёт физический файл примерно вида:

```text
data/exchange.mv.db
```

Каталог `data/` и файлы H2 исключены из Git.

## 24. Тесты

### 24.1. PersistentExchangeTest

Проверяет базовую функциональность биржи.

Сценарии:

- partial fill;
- full fill;

Это продолжение набора тестов первой лабораторной.

---

### 24.2. PersistentExchangeConcurrencyTest

Проверяет требование первой лабораторной о работе разных клиентов в разных потоках.

Используются:

- `ExecutorService`;
- пул потоков;
- `CountDownLatch`;
- `Future`.

Создаются 100 SELL и 100 BUY ордеров.

`CountDownLatch` заставляет задачи начать работу примерно одновременно.

После завершения проверяется:

- число сделок;
- суммарный объём;
- отсутствие открытых ордеров.

---

### 24.3. PersistentExchangeRestartTest

Главный новый тест второй лабораторной.

Содержит два типа перезапуска.

#### Штатный

1. создаётся биржа;
2. записывается ордер;
3. биржа закрывается;
4. создаётся новый объект с тем же путем к БД;
5. проверяется восстановленный ордер;
6. совершается сделка;
7. происходит ещё один restart;
8. проверяются сделка, остаток и уведомления.

#### Нештатный

1. запускается дочерняя JVM;
2. дочерний процесс создаёт ордера и сделку;
3. каждое `placeOrder` завершает свою транзакцию commit;
4. JVM аварийно завершается через `Runtime.halt(0)`;
5. родительский процесс открывает тот же файл;
6. проверяет историю сделок;
7. проверяет остаток ордера;
8. подключает клиентов;
9. проверяет восстановленные pending-уведомления.

---

### 24.4. AbruptTerminationWriter

Это вспомогательный класс для crash-теста.

Он не является частью бизнес-API.

Его задача:

- запуститься отдельным Java-процессом;
- открыть БД;
- выполнить операции;
- завершить JVM без штатного закрытия.

Если внутри возникает ошибка, процесс завершается другим exit code, чтобы JUnit увидел проблему.

# 27. Ответы на контрольные вопросы

## Вопрос 1. Как достигается сохранение состояния процесса после перезапуска?

Не сохраняется весь объект JVM как таковой.

Сохраняется именно бизнес-состояние системы:

- ордера;
- остатки ордеров;
- сделки;
- недоставленные уведомления.

Оно находится в файловой H2-БД.

Новый процесс открывает тот же файл БД и продолжает работу с теми же записями.

Online-listener не восстанавливается, потому что это объект конкретной JVM. Клиент после перезапуска подключается заново.

---

## Вопрос 2. Как достигается сохранность данных при нештатном завершении программы?

За счёт транзакций СУБД.

`placeOrder` выполняет связанные изменения в рамках одной транзакции и явно вызывает `commit`.

Если процесс завершится после commit, зафиксированные данные остаются в БД.

Если ошибка произойдёт до commit, транзакция не должна считаться завершённой целиком.

Работа отдельно проверяет crash-сценарий через дочернюю JVM и `Runtime.halt(0)`.

---

## Вопрос 3. На что влияет сохранение состояния программы в хранилище?

Появляются преимущества:

- данные переживают restart;
- можно восстанавливать состояние;
- появляется транзакционная целостность;
- можно хранить историю;
- легче разделять процессы на следующих этапах развития системы.

Но появляется цена:

- дисковые операции;
- SQL;
- JDBC;
- транзакции;
- дополнительная обработка ошибок;
- задержка выше, чем у обычной коллекции в RAM;
- необходимо проектировать схему данных и индексы.

# 28. Потенциальные вопросы на защите

## Почему вторая лабораторная содержит функциональность первой?

Потому что по условию вторая работа расширяет предыдущую. Основной бизнес-сценарий не заменяется, а дополняется долговременным хранилищем.

---

## Почему удалена отдельная lab1?

Потому что `lab2` является накопительной реализацией: она включает исходный функционал и новые требования. Отдельная старая версия не нужна для запуска актуального решения.

---

## Почему выбран H2?

Это embedded СУБД, разрешённая форматом задания: не нужен отдельный сервер, есть JDBC, SQL, транзакции и файловое хранение.

---

## Почему не SQLite?

SQLite тоже подошла бы. H2 удобна тем, что является Java-native embedded базой и естественно подключается Maven-зависимостью.

---

## Что именно сохраняется?

Сохраняются ордера, остатки, сделки и недоставленные уведомления.

---

## Что не сохраняется?

Не сохраняются Java callbacks и факт TCP/Java-подключения клиента к текущему процессу. Это runtime-состояние.

---

## Почему onlineClients — обычный Map?

Потому что доступ к нему выполняется под общим `ReentrantLock`. Самому Map поэтому не требуется быть concurrent.

---

## Почему используется один общий lock?

Для лабораторной это простой способ гарантировать корректность сложной атомарной операции matching + JDBC transaction при нескольких потоках.

Минус — ограниченная параллельность. В промышленной бирже блокировки обычно делали бы более гранулярными, например по order book или валютной паре.

---

## Почему нельзя просто использовать synchronized коллекции?

Потому что надо атомарно выполнить не одну операцию с коллекцией, а целую последовательность SQL-действий.

---

## Что такое транзакция?

Набор операций с БД, который должен быть зафиксирован как единое согласованное изменение.

Основные идеи ACID:

- Atomicity — всё или ничего;
- Consistency — переход между корректными состояниями;
- Isolation — параллельные операции не должны ломать друг друга;
- Durability — зафиксированные данные переживают сбой.

В этой лабораторной особенно важна Durability.

---

## Зачем rollback?

Если внутри операции возникает SQL-ошибка, незавершённые изменения текущей транзакции откатываются.

---

## Что будет, если приложение упадёт до commit?

Транзакция не должна считаться успешно завершённой. При восстановлении используется последнее зафиксированное состояние.

---

## Что будет, если приложение упадёт после commit?

Данные уже зафиксированы и должны восстановиться при следующем запуске.

---

## Что будет, если приложение упадёт после отправки уведомления, но до его удаления?

После restart уведомление может прийти повторно.

Это at-least-once доставка.

---

## Может ли уведомление потеряться?

Дизайн специально сначала сохраняет pending-уведомление и делает commit, а только потом вызывает callback. Поэтому crash до callback не уничтожает информацию о необходимости доставки.

---

## Почему pending_notifications хранит trade_id, а не всю сделку?

Чтобы не дублировать данные. Полная сделка уже лежит в `trades`, а notification хранит ссылку на неё.

---

## Почему полностью исполненные ордера не удаляются?

Они нужны как история. Их можно отличить по `remaining_quantity = 0`.

---

## Как определяется открытый ордер?

```text
remaining_quantity > 0
```

---

## Почему нужен originalQuantity, если есть remainingQuantity?

Чтобы знать исходный объём и вычислять, какая часть ордера уже исполнена.

---

## Может ли один ордер породить несколько сделок?

Да. Если большой входящий ордер последовательно сопоставляется с несколькими встречными ордерами.

---

## Почему цена сделки не обязательно равна цене входящего ордера?

В текущей модели используется цена resting-ордера. Входящий ордер задаёт предельное условие, по которому он согласен исполниться.

---

## Что такое price-time priority?

Приоритет сначала по лучшей цене, затем по времени постановки заявки.

В реализации временной порядок отражён возрастающим `id`.

---

## Почему время представлено id, а не timestamp?

Для определения порядка достаточно монотонно возрастающего идентификатора. Это проще и детерминированнее для данной лабораторной.

---

## Почему BigDecimal, а не double?

Денежные значения не стоит считать через binary floating point из-за ошибок представления дробей. `BigDecimal` даёт контролируемую десятичную арифметику.

---

## Зачем отдельный AbruptTerminationWriter?

Если завершить тот же JVM-процесс, который выполняет JUnit, сам тест прекратится. Поэтому crash моделируется дочерним процессом.

---

## Почему Runtime.halt, а не System.exit?

`halt` ближе к жёсткому завершению: JVM прекращается без нормальной процедуры shutdown.

---

## Как тестируется многопоточность?

Разные клиентские запросы запускаются как отдельные задачи `ExecutorService`.

`CountDownLatch` создаёт общий момент старта, чтобы обращения действительно конкурировали за один экземпляр биржи.

---

## Что является главным отличием lab2 от lab1?

В lab1 источником истины была оперативная память.

В lab2 источником истины стала H2-БД.

Именно поэтому состояние сохраняется между процессами.

# 29. Ограничения текущей реализации

Эти ограничения не являются ошибками лабораторной, но полезно их понимать.

### Один lock на всю биржу

Все валютные пары сериализуются через один `ReentrantLock`.

Для учебного проекта это упрощает корректность.

Для большой системы можно было бы блокировать отдельные order books.

### Нет отмены ордера

Условие работы этого не требует.

### Нет авторизации

`clientId` принимается как логический идентификатор.

Аутентификация не входит в задачу.

### Нет сетевого протокола

Во второй работе интерфейс остаётся Java API.

Сетевое взаимодействие относится к следующей лабораторной.

### Нет exactly-once доставки

Используется at-least-once.

Для exactly-once потребовался бы дополнительный механизм подтверждений и дедупликации.

### Нет отдельного Repository-слоя

JDBC находится непосредственно в `PersistentExchange`.

Для текущей лабораторной это оставляет реализацию компактной. При дальнейшем усложнении систему можно разделить на слои.

# 30. Что важно запомнить к защите

Если нужно объяснить лабораторную очень коротко:

> В первой версии биржа хранила состояние в памяти. Во второй я сохранил тот же публичный API и бизнес-логику, но перенёс ордера, сделки и недоставленные уведомления в embedded H2. Каждая операция placeOrder выполняется транзакционно. Сначала данные фиксируются commit-ом, затем доставляются уведомления. Поэтому после обычного restart и после аварийного завершения уже зафиксированное состояние восстанавливается. Многопоточность защищена ReentrantLock, а crash-сценарий проверяется отдельной JVM через Runtime.halt(0).

Это главная идея всей работы.
