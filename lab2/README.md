# Лабораторная работа №2 — встроенное хранилище данных

Вариант 1: **биржа валют**.

## 1. Что требуется по методичке

Вторая лабораторная является продолжением первой.

Нужно сохранить прежнюю бизнес-логику биржи и добавить долговременное хранение всех бизнес-данных во встроенной СУБД.

После перезапуска программа должна получить то же состояние, которое было до завершения.

Также тесты должны проверять:

- штатное завершение;
- нештатное завершение;
- отсутствие потери уже зафиксированных данных.

Для встроенного хранилища в этой реализации используется **H2**.

Важно: эта работа намеренно не добавляет функции, которых нет в задании. Здесь нет авторизации, балансов, комиссий, отмены ордеров, сетевого API, REST, Docker и других возможностей следующих лабораторных.

Биржа по-прежнему умеет:

Количество добавлено к ордеру потому, что без количества невозможно реализовать требуемое условием частичное исполнение.

## 5. Публичный интерфейс Exchange

Клиент работает через интерфейс `Exchange`.

### connect

```java
void connect(String clientId, NotificationListener listener)
```

Клиент считается online в текущем процессе.

В память сохраняется callback `NotificationListener`.

После подключения система проверяет, есть ли для этого клиента сохранённые offline-уведомления в БД. Если есть, они передаются через listener.

### disconnect

```java
void disconnect(String clientId)
```

Клиент перестаёт считаться online.

Его ордера и сделки не удаляются.

### placeOrder

```java
Order placeOrder(
    String clientId,
    CurrencyPair pair,
    OrderSide side,
    BigDecimal quantity,
    BigDecimal limitPrice
)
```

Создаёт лимитный ордер и пытается выполнить его против уже существующих совместимых ордеров.

### getOpenOrders

Возвращает незакрытые ордера по валютной паре.

Этот метод удобен для тестов и демонстрации восстановления состояния.

### getTrades

Возвращает сохранённые сделки.

Он также используется тестами и демонстрационным Main.

## 6. NotificationListener

Это обычный Java callback:

```java
@FunctionalInterface
public interface NotificationListener {
    void onTrade(TradeNotification notification);
}
```

Если клиент online, callback вызывается после успешного сохранения сделки.

Если клиент offline, callback вызвать невозможно, поэтому уведомление сохраняется в H2.

После будущего `connect` это уведомление считывается и передаётся клиенту.

## 7. Модели

### CurrencyPair

Хранит две валюты:

- base;
- quote.

Например:

```text
EUR/USD
```

Класс проверяет, что значения не пустые и валюты не совпадают.

### OrderSide

Два направления:

```text
BUY
SELL
```

### Order

Содержит:

- id;
- clientId;
- валютную пару;
- направление;
- limitPrice;
- originalQuantity;
- remainingQuantity.

`originalQuantity` — первоначальный объём.

`remainingQuantity` — сколько ещё не исполнено.

Пример:

```text
BUY 10
сделка на 4
remaining = 6
```

### Trade

Факт совершённой сделки.

Содержит:

- id сделки;
- валютную пару;
- цену;
- количество;
- id BUY-ордера;
- id SELL-ордера;
- buyerId;
- sellerId.

### TradeNotification

Уведомление конкретному клиенту о совершённой сделке.

## 8. PersistentExchange

Это основная реализация второй лабораторной.

Она:

- реализует `Exchange`;
- открывает H2;
- создаёт таблицы при первом запуске;
- записывает ордера;
- ищет встречные ордера;
- создаёт сделки;
- обновляет остатки;
- сохраняет offline-уведомления;
- восстанавливает данные при новом запуске;
- синхронизирует доступ из разных потоков.

Также класс реализует `AutoCloseable`, поэтому его удобно использовать через:

```java
try (PersistentExchange exchange = new PersistentExchange(path)) {
    ...
}
```

## 9. Почему H2

Методичка разрешает встроенные СУБД.

H2 подходит для учебной работы, потому что:

- работает внутри Java-приложения;
- не требует отдельного сервера;
- подключается Maven-зависимостью;
- поддерживает JDBC;
- поддерживает SQL;
- поддерживает транзакции;
- может хранить данные в файле.

База открывается в file mode.

По умолчанию Main использует:

```text
data/exchange
```

Физически H2 создаёт файл примерно:

```text
data/exchange.mv.db
```

Он не коммитится в Git.

## 11. Как определяется встречный ордер

Методичка не задаёт отдельный биржевой алгоритм приоритета между несколькими подходящими заявками.

Поэтому реализация использует простое детерминированное правило:

**берётся самый ранний совместимый ордер по id.**

Для входящего BUY подходит SELL, если:

```text
SELL.limitPrice <= BUY.limitPrice
```

Для входящего SELL подходит BUY, если:

```text
BUY.limitPrice >= SELL.limitPrice
```

Это не заявляется как отдельный биржевой механизм price-time priority — это лишь простой способ однозначно выбрать один из совместимых ордеров в рамках лабораторной.

Цена создаваемой сделки берётся из уже существующего встречного ордера. Методичка отдельно не определяет правило расчёта цены сделки, поэтому это внутреннее детерминированное решение реализации.

## 12. Частичное исполнение

Это важное требование первой лабораторной, которое сохраняется во второй.

Количество сделки:

```text
min(remaining incoming order, remaining existing order)
```

Пример:

```text
BUY 10
SELL 4
```

После сделки:

```text
BUY remaining = 6
SELL remaining = 0
```

BUY остаётся открытым.

Если затем приходит SELL 6, BUY закрывается полностью.

## 13. Что происходит в placeOrder

Упрощённая последовательность:

1. проверяются входные данные;
2. берётся `ReentrantLock`;
3. новый ордер записывается в БД;
4. ищется совместимый встречный ордер;
5. рассчитывается объём сделки;
6. обновляются остатки обоих ордеров;
7. создаётся запись сделки;
8. если участник offline — для него сохраняется pending notification;
9. если участник online — уведомление запоминается для отправки;
10. если у входящего ордера остался объём, matching продолжается;
11. выполняется `commit`;
12. online-клиенты получают callbacks.

То есть сначала фиксируется состояние БД, затем выполняются обычные уведомления online-клиентам.

---

## 14. Зачем нужны транзакции

Во второй лабораторной особенно важно требование переживать нештатное завершение.

В конструкторе:

```java
connection.setAutoCommit(false);
```

Изменения фиксируются явно:

```java
connection.commit();
```

Если происходит SQL-ошибка:

```java
connection.rollback();
```

Таким образом связанные изменения одного `placeOrder` не должны оставаться наполовину выполненными.

Например, нежелательно получить состояние:

```text
remaining_quantity уменьшился
но запись Trade не появилась
```

Транзакция нужна именно для согласованности таких связанных действий.

---

## 15. Что происходит при штатном завершении

`PersistentExchange` реализует `AutoCloseable`.

Метод `close()`:

- фиксирует незавершённые изменения;
- закрывает JDBC Connection.

После этого можно создать новый экземпляр с тем же путём к файлу.

Он увидит сохранённые:

- ордера;
- остатки;
- сделки;
- pending notifications.

---

## 16. Что происходит при нештатном завершении

Отдельный тест запускает дочерний JVM-процесс.

Этот процесс:

1. открывает ту же H2;
2. выставляет ордера;
3. совершает сделку;
4. завершает JVM через:

```java
Runtime.getRuntime().halt(0);
```

При этом обычный `close()` объекта не вызывается.

После завершения дочерней JVM основной JUnit-тест снова открывает БД и проверяет, что успешно закоммиченные данные сохранились.

Так проверяется именно нештатное завершение, требуемое методичкой.

---

## 17. Что сохраняется, а что нет

### Сохраняется

- ордера;
- остатки ордеров;
- сделки;
- уведомления offline-клиентов.

### Не сохраняется

- Java `NotificationListener`;
- факт текущего подключения клиента.

Это нормально.

Listener существует только внутри конкретной JVM.

После перезапуска старого Java-объекта listener уже нет, поэтому клиент должен выполнить `connect` снова.

---

## 18. Потокобезопасность

По условию клиенты могут работать из разных потоков одного процесса.

Для защиты используется:

```java
ReentrantLock
```

Почему одной потокобезопасной коллекции недостаточно?

Потому что `placeOrder` — это не одна операция.

Он включает последовательность:

```text
INSERT order
SELECT matching order
UPDATE remaining
INSERT trade
INSERT pending notification
COMMIT
```

Нужно защищать всю эту последовательность целиком.

Для лабораторной один общий lock — простой и понятный вариант.

## 19. Тесты

### PersistentExchangeTest

Проверяет основной сценарий:

- BUY/SELL;
- частичное исполнение;
- полное исполнение;
- формирование сделок;
- остаток ордера;
- уведомления двум online-клиентам;
- сохранение уведомления offline-клиента;
- доставка после connect.

Здесь нет отдельного теста «лучшей цены», потому что такое правило методичкой не задано.

### PersistentExchangeConcurrencyTest

Проверяет одновременную работу клиентов.

Используются:

- `ExecutorService`;
- несколько потоков;
- `CountDownLatch`;
- `Future`.

BUY и SELL запросы стартуют конкурентно против одного экземпляра биржи.

После завершения проверяются:

- количество сделок;
- суммарный объём;
- отсутствие незакрытых встречных ордеров.

### PersistentExchangeRestartTest

Проверяет два новых требования второй работы.

#### Штатное завершение

Создаётся биржа, записывается состояние, объект закрывается, затем создаётся новый экземпляр с тем же файлом БД.

Проверяется восстановление состояния.

#### Нештатное завершение

Запускается отдельная JVM через `ProcessBuilder`.

Она записывает состояние и завершается через `Runtime.halt(0)`.

Основной тест снова открывает H2 и проверяет сохранённые данные.

### AbruptTerminationWriter

Вспомогательный класс для предыдущего теста.

Он нужен потому, что нельзя вызвать `Runtime.halt` внутри самого JUnit-процесса: тогда завершится и тестовый runner.

# 22. Ответы на контрольные вопросы

## 1. Как достигается сохранение состояния процесса после перезапуска?

Бизнес-состояние переносится из обычных Java-объектов в файловую H2-БД.

Ордера, сделки и offline-уведомления сохраняются SQL-записями.

После нового запуска `PersistentExchange` подключается к тому же файлу, поэтому ранее сохранённые данные снова доступны.

Сам процесс JVM не сохраняется — сохраняются данные, необходимые для восстановления бизнес-состояния.

---

## 2. Как достигается сохранность данных при нештатном завершении программы?

Изменения выполняются транзакционно.

После успешной операции вызывается `commit`.

Зафиксированные СУБД данные должны пережить аварийное завершение процесса.

Если SQL-операция завершается ошибкой до commit, выполняется rollback.

Нештатный сценарий проверяется отдельной JVM, завершаемой через `Runtime.halt(0)`.

---

## 3. На что влияет сохранение состояния программы в хранилище?

Появляются дополнительные затраты:

- запись на диск;
- SQL;
- JDBC;
- управление транзакциями;
- обработка ошибок БД.

По сравнению с хранением только в RAM работа становится сложнее и обычно медленнее.

Зато появляется главное преимущество: данные не исчезают после завершения процесса.

# 23. Возможные вопросы на защите

## Чем lab2 отличается от lab1?

В lab1 источником состояния является оперативная память.

В lab2 состояние находится в H2 и переживает restart.

---

## Почему обе папки сохранены, если lab2 продолжает lab1?

Чтобы каждая работа оставалась отдельным сдаваемым этапом.

`lab2` логически основана на первой, но преподаватель может захотеть посмотреть отдельно исходную in-memory реализацию и отдельно её развитие.

---

## Почему H2?

Это встроенная СУБД: не нужен отдельный сервер, есть JDBC и транзакции, данные можно хранить в файле.

---

## Почему количество есть в ордере, хотя в формулировке перечислены пара, направление и цена?

Потому что условие прямо требует частичного исполнения ордера.

Без количества невозможно определить, что именно исполнено частично.

---

## Зачем BigDecimal?

Цена и количество являются десятичными величинами.

`BigDecimal` не имеет характерных для `double` ошибок бинарного представления десятичных дробей.

---

## Почему online состояние не записывается в БД?

Подключение и Java listener относятся к текущему процессу.

После завершения JVM этот listener физически перестаёт существовать.

Поэтому после нового запуска клиент подключается снова.

---

## Что происходит с уведомлением offline-клиента?

Оно записывается в `pending_notifications`.

Когда клиент вызывает `connect`, уведомление загружается, передаётся listener и затем удаляется из таблицы.

---

## Почему online-уведомление не хранится в pending_notifications?

По ТЗ сохранять нужно уведомление клиента, который **не в сети**.

Если клиент online, после успешного commit ему вызывается callback напрямую.

---

## Зачем commit?

Чтобы явно зафиксировать изменения транзакции в БД.

Без commit при отключённом autoCommit изменения не считаются окончательно сохранёнными.

---

## Зачем rollback?

Чтобы при SQL-ошибке отменить незавершённые изменения текущей транзакции.

---

## Что произойдёт, если JVM упадёт после успешного commit?

Зафиксированное состояние должно сохраниться и быть доступно после повторного открытия БД.

---

## Что произойдёт, если JVM упадёт до commit?

Незавершённая транзакция не должна считаться успешно выполненной целиком.

---

## Почему не используется ConcurrentHashMap?

Потому что требуется защищать не только Map, а целую последовательность SQL-операций и matching.

---

## Зачем ReentrantLock?

Чтобы два клиентских потока не изменяли связанные данные одновременно и не ломали состояние ордеров и транзакции.

---

## Как имитируется одновременная работа клиентов?

Несколько задач запускаются через `ExecutorService`.

`CountDownLatch` удерживает их до общего сигнала, после чего они одновременно вызывают `placeOrder`.

---

## Зачем отдельный процесс для аварийного теста?

Если вызвать `Runtime.halt` внутри самой JVM JUnit, завершится и весь тестовый процесс.

Поэтому crash моделируется дочерней JVM.

---

## Почему Runtime.halt, а не обычный close?

Нужно проверить именно нештатное завершение, а не корректное закрытие ресурса.

---

## Каким образом выбирается один ордер, если совместимых несколько?

Методичка отдельное правило не задаёт.

В реализации берётся самый ранний совместимый ордер по id.

Это просто детерминированное внутреннее правило, а не дополнительное требование системы.

---

## Почему нет отмены ордера?

Она не требуется заданием.

---

## Почему нет авторизации и балансов?

Они не требуются заданием.

---

## Почему нет HTTP/TCP?

Сетевой интерфейс относится к следующей лабораторной.

# 24. Короткий ответ для защиты

Если нужно объяснить работу примерно за минуту:

> Это валютная биржа из первой лабораторной, но её состояние перенесено во встроенную H2. Клиент через Java-интерфейс выставляет BUY или SELL ордер с валютной парой, количеством и лимитной ценой. При встречном ордере создаётся сделка, остатки обновляются, online-клиенты получают callback, а для offline-клиента уведомление сохраняется в БД. Все связанные изменения выполняются через JDBC-транзакцию и commit, поэтому состояние переживает перезапуск. Есть тест обычного закрытия и отдельный crash-тест, где дочерняя JVM завершается через Runtime.halt(0). Работа разных клиентов из потоков проверяется через ExecutorService и CountDownLatch.

Это и есть основная суть лабораторной.
