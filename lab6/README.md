# Лабораторная №6 — шардирование валютной биржи

Продолжение `lab5` с сохранением разделения фасада, бизнес-логики и хранилища. Для шардирования используются три одинаковых комплекта Docker-контейнеров: `business-N`, `storage-N`, `database-N` для N от 0 до 2. Каждая база H2 имеет собственный постоянный Docker volume. Шарды хранят разные валютные пары; общая база для всех шардов отсутствует.

## Маршрутизация

Фасад принимает прежние текстовые UDP-команды. Внутреннее взаимодействие между фасадом, бизнес-слоем и хранилищем идёт по TCP с Protocol Buffers.

Шард для пары `base/quote` вычисляется одинаково у фасада и бизнес-сервиса: `floorMod((BASE + ":" + QUOTE).hashCode(), 3)`. Названия валют приводятся к верхнему регистру. Таким образом, одна валютная пара всегда обрабатывается одним бизнес-сервисом и хранится в одной БД. Бизнес-сервис проверяет принадлежность пары своему шарду. При фиксированном количестве шардов маршрутизация не меняется между перезапусками.

`PLACE_ORDER` и `GET_OPEN_ORDERS` направляются только в соответствующий шард. `GET_TRADES` запрашивает данные у всех трёх шардов, после чего фасад собирает единый список. Для уникальности внешние идентификаторы ордеров и сделок рассчитываются как `(localId - 1) * 3 + shard + 1`. Внутренние идентификаторы внутри H2 остаются локальными. Сопоставление ордеров выполняется только внутри одного шарда, включая частичное исполнение и уведомления обоих участников. Отложенные уведомления сохраняются в БД своего шарда и доставляются после подключения пользователя через фасад.

## Общая операция над всеми шардами

Новая UDP-команда отменяет все открытые ордера пользователя во всех валютных парах:

```text
CANCEL_ALL_ORDERS|requestId|clientId
```

Фасад рассылает `CANCEL_ALL` каждому бизнес-шарду, бизнес-слой отменяет ордера через своё хранилище в транзакции, фасад суммирует числа отменённых ордеров и возвращает:

```text
OK|requestId|CANCELLED|count
```

Открытым считается ордер с положительным `remaining_quantity`. Сама отмена устанавливает остаток в ноль, уже выполненные сделки сохраняются. Повторная отмена не меняет состояние и возвращает `0`. Глобальная операция представляет собой набор отдельных транзакций по шардам, а не одну распределённую транзакцию.

## Запуск

Требуется Docker Desktop. Из папки `lab6`:

```powershell
docker compose build
docker compose up -d facade
docker compose run --rm tests
```

Для просмотра контейнеров: `docker compose ps`. При подключении клиента с компьютера опубликованный UDP-порт фасада определяется через `docker compose port facade 9000/udp`. Остановка с сохранением данных: `docker compose down`. Команда `docker compose down -v` дополнительно удаляет все три тома данных лабораторной.

Для тестов в IntelliJ IDEA открой `lab6/pom.xml` как отдельный Maven-проект и запусти `test` в окне Maven. Требуется JDK 23 или новее. Генератор `protoc` не запускается: код формата `ExchangeWire.Packet` находится в `src/main/java`, что исключает проблему с кириллицей в пути Windows. Публичный UDP-протокол предыдущей лабораторной сохраняется, дополнен только командой отмены.

## Тесты лабораторной №6

В `src/test` находятся только тесты, относящиеся к шестой лабораторной:

- `ShardRoutingTest` — распределение пар, проверка принадлежности шарду, уникальные идентификаторы и Protobuf-сериализация нового ответа.
- `StorageShardOperationsTest` — отмена только собственных ордеров пользователя, повторная отмена и независимость баз данных.
- `FacadeShardAggregationTest` — объединение сделок и результатов отмены с нескольких шардов.
- `DockerShardingIntegrationTest` — реальные UDP-запросы к трём шардам в Docker, сделка, доставка уведомления после подключения, сохранение чужих ордеров и глобальная отмена.

Интеграционный Docker-тест запускается при наличии `EXCHANGE_HOST` внутри контейнера `tests`. Обычный локальный запуск тестов не требует работающего Docker.
